# Performance report: G3a (factions + skirmish), 2026-10-23

- **Hardware:** AMD Ryzen 5 8640HS (12 logical cores), Radeon 760M integrated GPU, 15.3 GiB RAM, Windows 11.
- **Build:** Godot 4.7.2-stable official, run from source (editor runtime), Compatibility renderer.
- **Code:** commit `e8a8464` (all G3a sim + AI code committed; working tree had only doc/.uid changes).
- **Conditions:** quiet machine (no soaks or tests running alongside). The earlier 22.5 ms at 256 units was measured under load and is superseded by this report.

For comparison, the G2 report measured 45–53 fps at ~210 units and 21–24 fps at ~440 units with 2 sides.

## Known gap: 3-side frame rate at 250+ units

- With 3 sides and about 250–400 units, the frame rate falls to **10–21 fps**. With 2 sides at a similar count it is 34–45 fps.
- **The cause is not isolated.** A headless per-system profile (`--spawn-test` fight replicated in a scratch script, 400 ticks per configuration, run in one process) was inconclusive:
  - timings fell steadily with run order by up to 2x, whichever configuration ran first;
  - in two runs with the order reversed, the "3 sides is slower" result flipped.
  - In both runs, combat and movement were about 75% of tick cost, and fog, AI and supply were 1–2.5 ms each.
- The two windowed runs were also not equal fights: more units were still alive in the 3-side run at the same tick, so more combat was happening.
- **Next step:** measure each configuration in a separate process at a matched unit count. If the gap holds, profile the 3-side fight in the windowed build. The structural fix is still the G4 sim worker thread (rendering currently waits on the sim).

## Not measured / caveats
- 1,000+ units.
- Memory per N; long-session memory growth.
- An exported release build (only the editor runtime with a packed .pck).
- Other hardware.
- 4-side (2v2) windowed fps.
